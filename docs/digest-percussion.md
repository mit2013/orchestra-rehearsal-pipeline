# アマオケ練習録音パイプライン ― ダイジェストの取りこぼしを直す(打楽器と弱奏)

> **この指示書は実施済みである。** 当初案のうち §2-2 の「音量の上位パーセンタイル」と
> 「打楽器向けの積極的な証拠」は実測で否定され、別の対策に置き換わった。経緯を
> 残したうえで、確定した内容に書き直してある。実測値は §5 を参照。

## 0. 位置づけ

260829 のダイジェストを試聴して2つの問題が見つかった。

1. **打楽器だけの長いクレッシェンドが丸ごと落ちる**(演奏部の欠落)。260726・260802 は
   打楽器のない日だったため、これまで表面化していなかった。
2. **ダイジェストの冒頭にチューニングが入る**。ダイジェストの目的からして不要。

いずれも `orchpipe/research/states2.py` の分類と `digest.py` の範囲決めに手を入れる。
チューニング検出そのものの欠陥は別件で、
`tuning-detection.md` を参照。

## 1. ブランチ

`research/fine-segmentation` から `research/digest-percussion` を作成する。本番コード
(`pipeline.py` と `orchpipe/` 直下)には触れないこと。ただし
`orchpipe/research/tuning.py` は例外で、本番の `orchpipe/tuning.py` を再輸出する形に
一本化する(§3-2 の理由による)。

`feature/audio-quality` が main にマージされたあとに切ること。切る前に
**main を `research/fine-segmentation` に取り込むこと**。

## 2. 演奏の取りこぼし

### 2-1. 何が起きているか

`states2.playing_confidence` は**調和性(倍音系列で説明できるエネルギーの割合)だけ**で
実質的に決まる。補助指標(安定性・オンセット密度)は `AUX_WEIGHT` の範囲でしか効かない。
しきい値 `H_CENTER = 0.205`、傾き `H_SLOPE = 80.0` である。

260829 後半の1・3・4楽章の通し稽古(計 39.8 分。範囲は人に確認済み)を正解データとして
採点すると、**166.2 秒(7.0%)を取りこぼしていた**。原因は3種類に分かれる。

| 種類 | 調和性 | 例 |
|---|---|---|
| 打楽器・アタック主体 | 0.00〜0.15 | 3楽章冒頭のティンパニ、中盤のクレッシェンド |
| しきい値ぎわの往復 | 0.17〜0.20 | 1楽章冒頭、通しの途中 |
| 弱奏が無音に負ける | 0.20〜0.23 | 4楽章 Urlicht |

打楽器のロール(ティンパニ・シンバル・大太鼓)は倍音系列を持たないため、調和性が
上がらない。260829 中盤 **19:11–19:40 の30秒**、打楽器群だけのクレッシェンドの実測:

| 時刻(中盤内) | 調和性 | 確信度 | RMS | 当時の判定 |
|---|---|---|---|---|
| 19:10 | 0.224 | 0.99 | −48.9 dB | playing |
| 19:20 | 0.105 | 0.00 | −58.2 dB | unclear |
| 19:30 | 0.053 | 0.00 | −34.2 dB | unclear |
| 19:38 | 0.136 | **0.00** | **−14.7 dB** | unclear |
| 19:42 | 0.224 | 0.86 | −35.5 dB | playing |

**ブロック中でもっとも大きい部類の −14.7 dBFS ですら確信度 0.00 である。**
現行の分類器は**音量をまったく見ていない**。

### 2-2. 直したこと

以下の4つを実装した。定数と根拠は `states2.py` の冒頭に書いてある。

**(1) 調和性のヒステリシス**

`HYST_ENTER_H = 0.215` で演奏に入り、`HYST_STAY_H = 0.185` を割るまで抜けない。
しきい値のすぐ両側を行き来するため、ひと続きのフレーズの中で確信度が 1.00 と 0.00 を
1〜2秒おきに往復していた(260829 後半 00:31:31–00:32:01 は最大 −11.0 dBFS の
トゥッティだが、判定は6回反転した)。

**(2) 音量による playing の上書き ― 無音閾値からの相対量で持つ**

当初案は「ブロック内の窓 RMS の上位10パーセンタイル以上は調和性を問わず playing」
だった。**実測するとほとんど効かなかった。**

| 設定 | 取りこぼし |
|---|---|
| 現行 | 251.8 秒 |
| 上位10%(当初案) | 251.8 秒 |
| 上位20% | 244.2 秒 |

理由は単純で、**ソロのティンパニはブロックの上位10%に入らない**。260829 3楽章冒頭の
打撃は最大 −20.0 dBFS で、ブロックの窓 RMS の90%点は −19.9 dBFS。トゥッティ
(−11〜−17 dBFS)が上位を占めるので、ソロは相対的に「小さい音」になってしまう。
中盤のクレッシェンドが救えたのは、あれが −14.7 dBFS とトゥッティ並みだったからである。

そこで **`LOUD_MARGIN_DB = 14.0`、つまり無音閾値 +14 dB を超える窓は調和性を問わず
playing** とする。260829 後半でこの値が拾う発言窓は 309 窓中 2 窓(0.6%)だけだった。

**(3) 無音判定を演奏の証拠に譲らせる**

`classify` は `silence → tuning → speech → playing` の順に確定させる作りで、silence が
最優先だった。マーラー2番4楽章(Urlicht)のような弱奏は、調和性が 0.20〜0.23 と演奏を
示しているのにレベルが無音閾値を割るため消えていた。実測でアタッカ以降の窓の 13.1% が
silence とされ、**そのうち 29/62 は調和性がしきい値を超えていた**。

`sil = (rms < silence_db) & ~(h > H_CENTER)` として、演奏の証拠が立つ窓は無音にしない。

**(4) 文脈による橋渡し(`bridge_playing`)**

弱音のトレモロは、窓ひとつを見る限り本物の無音と**区別がつかない**。260829 1楽章
00:45:56–00:46:40(人が「44秒間ずっと演奏中」と確認)の実測:

| | RMS | 調和性 | 安定性 | フラックス |
|---|---|---|---|---|
| pp トレモロ | −50.7 | 0.151 | 0.878 | 0.206 |
| 本物の無音 | −51.5 | 0.159 | 0.825 | 0.217 |

どの指標でも分離しない。救えるのは文脈だけである。そこで **playing に挟まれた非 playing
の連なりを playing に倒す**。`fill_playing_gaps` との違いは、silence をまたげることと、
unclear と silence が入り混じった連なりをひとまとまりで扱うことである。

無条件に倒すと部分練習の日に待ち時間を拾う。260802 合奏2 で足された箇所を人が聴いた
ところ、**11件中8件が「無駄時間(入れてはいけない)」、「演奏している」は0件**だった。
そこで4つの条件をかけてある。

| 条件 | 定数 | 根拠 |
|---|---|---|
| 発言・チューニングを含む隙間は対象外 | `BRIDGE_STOP_LABELS` | 指揮者が止めれば必ず何か言う。チューニングは §3 の除外に使う |
| 8秒を超える連続無音があれば対象外 | `BRIDGE_MAX_SILENCE_RUN_S = 8.0` | 通し稽古の隙間126件の連続無音は最長8秒(99%が5秒以内)。通しの外には14〜17秒があった |
| 3秒未満の playing は足場にしない | `BRIDGE_MIN_PLAY_S = 3.0` | 無駄時間の隙間は**後ろ側の playing が中央1.5秒**。演奏の再開ではなく単発のノイズだった |
| 前後の演奏がともに10秒以上 | `BRIDGE_MIN_FLANK_S = 10.0` | 救うべき隙間は後ろ側の playing が中央22.5秒 |
| 隙間の長さの上限 | `BRIDGE_MAX_S = 30.0` | 30秒で効果が飽和する |

長さの上限だけでは分離しない。上限を15秒に詰めても無駄時間8件のうち4件が残り、
そのとき通し稽古の取りこぼしは37秒に増えた。**分けているのは長さではなく
「前後で演奏が続いているか」である。**

### 2-3. 採用しなかったもの ― 打楽器のモード比

当初案には「調和性が低くても、スペクトル平坦度が高く持続する窓は打楽器として playing」
という項があった。これを、より具体的な**ティンパニの振動モード比**として検証した。

ティンパニの膜のモードは整数倍ではなく **1 : 1.5 : 2 : 2.44 : 2.9** に並ぶ。260829
3楽章冒頭の打撃を手で切り出してスペクトルを見ると、98 Hz(G2)と 130 Hz(C3)の上に
1.55 倍・2.0 倍の成分がはっきり立っており、指紋としては本物だった。

**しかし自動判定には使えない。1.5 という比は完全5度そのものだからである。**
低音に根音と5度がある和音なら必ず立つ。全窓に当てた実測:

| | 基音の1.5倍に立つ成分の相対強度(中央) | 0.35 以上の割合 |
|---|---|---|
| 通常の合奏 | 0.22 | 29% |
| ティンパニ | 0.26 | 30% |

分離しない。条件をどう締めても、ティンパニ窓の発火率 21% に対し通常の演奏 7.1%、
無音 3.6% が精一杯で、証拠として使えば無音を大量に playing にしてしまう。
**採用しない。**

3楽章冒頭のティンパニは (2) の音量上書きと (4) の橋渡しで大部分が救われる。残るのは
楽章の先頭の 9.1 秒で、ここは前に演奏がないため橋渡しが成立しない。

## 3. ダイジェストにチューニングが入る

### 3-1. 何が起きているか

`states2` は `tuning` クラスを持つが、機能したりしなかったりする。260829 の実測:

| ブロック | tuning と判定された長さ | 実際のチューニング |
|---|---|---|
| 合奏1 | 18秒(ただし冒頭は 4.2–105.5 秒がまるごと playing) | 約71秒 |
| 合奏2 | 26.1秒 | 約36秒 |
| 合奏3 | 19.5秒 | 約34秒 |

合奏1ではチューニングがほぼ playing に分類され、ダイジェストの冒頭に約100秒の
チューニングがそのまま入っていた。

### 3-2. 直したこと

**分類器の tuning クラスの精度に頼らない。** 境界を決める段階でチューニングの位置は
既に正確に分かっている(ブロック開始 = チューニング開始、`TUNING_PRE_ROLL_S`)。
そこで範囲を決めたあとに、**ブロック先頭からチューニング終了までを無条件に落とす**
(`digest.head_tuning_end` と `digest.drop_head`)。検出できなかった場合は安全側に
倒してブロック先頭から `HEAD_SKIP_S = 90` 秒を落とす(`--head-skip`、負値で無効)。

チューニング検出には本番の `orchpipe.tuning` を使う。**研究側に残っていた旧実装のままでは
この機能は成立しない。** 実際 `output/260829/research/03_合奏3_tuning.json` は、旧実装が
演奏中の C#6 を拾った 328 秒の位置を唯一のチューニングとして記録していた。そこで
`orchpipe/research/tuning.py` は本番モジュールの再輸出に置き換えた。

あわせて `bridge_playing` が tuning クラスをまたがないようにした。チューニングは前後を
演奏に挟まれ発言も伴わないため、そのままでは playing に塗り潰されて除外の判断ができない。

## 4. 評価の方針

**圧縮率は評価指標にしない。** 圧縮率はその日の練習の中身で決まってしまう。通し稽古が
中心の日は実際に演奏し続けているので短くなりようがなく、部分練習が中心の日は指示や
待ち時間が多いので大きく縮む。指揮者によっても話す量が違う。つまり圧縮率は分類器の
性能ではなく**その日の練習の性質**を測ってしまう。

見るのは次の2つである。

- **正解データに対する取りこぼし秒数。** 通し稽古(楽章まるごとを止めずに演奏する練習)の
  区間が使える。ただし指揮者が途中で止めることがあるので「範囲内はすべて playing」と
  機械的に決めつけず、範囲と停止の有無を人に確認すること。
- **人手評価。** 足された区間が本当に演奏か、待ち時間かを聴いて判定してもらう。

## 5. 実施結果

### 5-1. 260829 後半(通し稽古39.8分が正解)

| | 取りこぼし | playing |
|---|---|---|
| 現行 | 166.2 秒 (7.0%) | 60.7 分 |
| 橋渡しなし(1〜3のみ) | 134.1 秒 | — |
| 条件なしの橋渡し | 13.0 秒 | 69.9 分 |
| **確定した設定** | **35.6 秒 (1.5%)** | **63.8 分** |

楽章別の内訳は 1楽章 18.7 秒 / 3楽章 9.1 秒 / 4楽章 7.8 秒。残る主なものは:

| 箇所 | 長さ | |
|---|---|---|
| 00:58:53 | 9.1秒 | 3楽章冒頭のティンパニ。楽章の先頭で前に演奏がなく橋渡しが成立しない |
| 00:57:17 | 8.4秒 | 1楽章末尾。指揮者が話し始める直前で、切れて正しい可能性が高い |
| 00:34:15 / 00:34:30 | 3+6秒 | 1楽章冒頭のトレモロ+低弦 |
| 01:11:52 / 01:15:32 | 3+3秒 | 4楽章 Urlicht の弱奏 |

中盤 19:11–19:40 の打楽器クレッシェンドは、30秒の欠落が消えて657秒の連続 playing に
含まれるようになった。

### 5-2. 260802 合奏2(人手評価)

無駄時間と判定された8件のうち**7件を除外**した。残る1件(01:15:14)は無音閾値を
上回っており、橋渡しではなく別の経路で playing になっている。話している時間も短いので
無理に除外しない。

playing の総量は 49.4 → 51.0 分(条件なしの橋渡しでは 61.8 分だった)。

### 5-3. チューニングの除外(260829 合奏1)

検出 4.7–82.2 秒(純度 0.80)を除外。ダイジェスト冒頭40秒で A のオクターブに載る
フレームが **73.5% → 6.2%**。チューニング直後の演奏の入り(00:01:22 以降)は
削れていない。
