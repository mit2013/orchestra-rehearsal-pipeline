## 0. エグゼクティブサマリ

アマチュアオーケストラの練習録音(ZOOM M4 MicTrak、4ch/32bit float、1回あたり約3時間)を、
SDカードからの取り込みから、不要区間の自動判定、正規化、曲目単位のエクスポート、
クラウド配布、通知までを一気通貫で自動化するパイプラインを構築した。

- **開発期間**: 2026-08-13 23:06 〜 2026-08-15 17:03(暦日で3日、経過 42.0 時間)
- **コミット数**: 22
- **実装コード**: Python 23ファイル / 4,555 行(うちコード 3,086 行)
- **処理した実データ**: 2セッション、計 6.28 時間、元素材 16.2 GiB
- **クラウド転送**: 8.73 GiB(Box 0.75 GiB / Google Drive 7.97 GiB)
- **外部API連携**: Box(OAuth2)、Google Drive(OAuth2)、LINE Messaging API の3系統

技術的な中心は「**無音検出では判定できない不要区間を、音響的特徴の組み合わせで判定する**」
部分にある。当初の閾値+ヒステリシス方式は実データで破綻し、2状態のビタビ探索に置き換えた。
さらに、良かれと思って入れた平滑化が最大の誤差要因だったことがアブレーションで判明し、
既定で無効化した。この2段階の設計変更により、**「本物の演奏を削ってしまった量」が
982秒 → 0秒**になった。

## 2. 開発の時系列と意思決定の流れ

コミットメッセージだけでは「何を変えたか」しか分からない。ここでは各変更が
**なぜ必要になったか**を、きっかけとなった実データ・実測値とともに再構成する。

### 2.1 フェーズ1: 初期実装(8/13 23:06, `8d39779`, +2,196行)

指示書 `phase1.md`(115行)から一気に 13ファイル・2,196行を実装。この時点で
`ingest` / `merge` / `propose` / `apply` の4サブコマンドと、特徴量抽出・区間判定の
中核が揃った。

この初期実装の中で、**コミット前に3つの設計変更**が行われている。git履歴には
単一コミットとして残るため見えないが、開発過程としては重要な転換点である。

#### 転換点A: WAV 4GB制限 → RF64 [セッションログ]

`ffprobe` で実データを確認した段階で、結合後のサイズが問題になることが判明した。

```
260802: 5591s + 5545s = 11,136 秒
ステレオ f32: 11,136 × 48,000 × 8 バイト = 4,276,224,000 バイト
WAV の RIFF サイズ上限: 4,294,967,295 バイト
→ 余裕はわずか 18 MB
```

TAKEが1本増えれば確実に破綻するため、`-rf64 auto` を指定する判断をした
(`orchpipe/merge.py`、コミットメッセージ `8d39779` にも記載)。
**この判断は後に実際に効いた**。260726(3.19時間)では 4.10 GiB となり、
RF64 が実際に発動した(ヘッダが `RIFF` から `RF64` に切り替わったことを確認)[セッションログ]。

#### 転換点B: 閾値+ヒステリシス → 2状態ビタビ探索 [セッションログ]

当初は「合奏らしさスコア」に対し、大津の方法で閾値を決め、ヒステリシスで
2値化する実装だった。実データ(260802、3時間)に適用した結果:

```
1. 00:00:00 - 01:08:48  [削る] 音出し    68.8分
2. 01:08:48 - 01:17:23  [残す] 合奏1      8.6分
3. 01:17:23 - 01:46:45  [削る] 休憩      29.4分
4. 01:46:45 - 02:13:32  [残す] 合奏2     26.8分
5. 02:13:32 - 03:05:36  [削る] 片付け    52.1分
```

3時間の練習で「音出し69分・片付け52分」は明らかに実態と乖離している。
原因を特徴量レベルで調査したところ、スコアが窓ごとに大きく振れており
(5分平均で −2.8 〜 +6.2)、閾値付近でのばたつきが区間を細切れにし、
その後の最小長補正が連鎖的に破綻していた。

**設計変更**: 「窓ごとのスコア合計」と「状態を切り替える回数」のトレードオフを
全体最適で解く2状態ビタビ探索に置き換えた(`orchpipe/segment.py` の `_viterbi`、
`_fit_penalty`)。`--splits N` を指定すると、合奏区間がちょうどN個になる
遷移ペナルティを対数スケールで二分探索する。

結果:

```
1. 00:00:00 - 00:21:19  [削る] 音出し    21.3分
2. 00:21:19 - 01:30:26  [残す] 合奏1     69.1分
3. 01:30:26 - 01:41:02  [削る] 休憩      10.6分
4. 01:41:02 - 03:00:38  [残す] 合奏2     79.6分
5. 03:00:38 - 03:05:36  [削る] 片付け     5.0分
```

波形画像による裏付けも得られた。**音出し区間と休憩区間の波形が視覚的にほぼ同一**
(−25dB前後の途切れない帯、ダイナミクスなし)で、合奏区間の断続的な深い無音と
明確に異なっていた。これは指示書 §4 の記述

> **音出し・休憩中**: 各奏者がバラバラに個人練習しており、リズムの統一感がなく、
> ダイナミクス(強弱)のメリハリが乏しい。強音が途切れず連続する傾向があり、
> 無音区間はむしろ少ない。

が実データで確認できた瞬間でもある。

#### 転換点C: 閾値の非対称化 [セッションログ]

大津の方法は「合奏が全体の7割」のような偏った分布では合奏側に食い込んだ位置を返す。
実測で大津の閾値は 2.07、望ましい谷は約 1.0 だった。

そこで **2クラス中心間距離の25%だけ低いほうへずらす**設計にした
(`orchpipe/segment.py` の `decision_threshold`)。理由はコード内コメントに残っている:

> 本物の合奏を削ってしまう誤りは、音出しが少し残る誤りよりはるかに痛いので、
> 意図的に「残す側」へ倒している。

この「誤りの非対称性を設計に組み込む」という考え方は、後の `--guard`(§2.3)にも一貫する。

### 2.3 転換点D: 平滑化の廃止 ― アブレーションによる原因特定 [セッションログ]

3つの仮説はいずれも部分的に正しかったが、**主犯は別にあった**。
他の条件を固定し、300秒の中央値フィルタだけを外すアブレーションを行った:

| 設定 | b1 | b2 | b3 | b4 | **演奏を削った量** |
|---|---|---|---|---|---|
| 平滑化 300s(当時の既定) | +757s | −23s | −52s | −202s | **982s** |
| 平滑化なし | +95s | −13s | −52s | −102s | **210s** |

**平滑化と Viterbi の遷移ペナルティは同じ仕事(短い変動の無視)をしていた。**
違いは、ペナルティは境界を動かさずにそれを行うのに対し、中央値フィルタは
時間分解能を捨てて行う点にある。両方を重ねると、コストだけ二重に払っていた。

さらに平滑化長を振ると、60秒を超えると再び破綻することが分かった:

| 平滑化 | 最大誤差 |
|---|---|
| なし | 102s |
| 30s | 102s |
| 60s | **971s** |
| 300s | 757s |

3つの仮説の検証結果も定量化された:

- **仮説1(誤検出)**: 該当。ただし**向きが逆**だった。音出し中の誤検出ではなく、
  早期に検出された8件のチューニング(00:10:03〜00:21:19)が**すべて合奏1の内部**だった。
  逆に 00:08:42 直前にあるはずの本物のチューニングは1件も検出できていない
  (音出し中は全員が鳴らしていて基準音がマスクされるため)。
- **仮説2(アンカー不在)**: 事実として確認。03:04:00 の前後10分にチューニング検出は0件。
- **仮説3(端での精度低下)**: 該当。機構も特定できた。端の区間は遷移ペナルティを
  1回しか払わない代わりに、自身の長さだけで元を取る必要がある。`--splits 2` が
  強制するペナルティ 28.55 に対し、1.6分の片付け(約19窓)では足りず、
  DPは元が取れる長さになるまで境界を内側へ押し込む。

加えて、`--min-remove` の既定値 2.5分が実際の片付け 1.6分より長く、
**正しい境界が構造的に採用され得なかった**ことも判明した。

**対策(4点)**:
1. `--smooth` 既定 300 → **0(無効)**
2. `--guard` 新設(既定120秒): keep区間を外側へ広げる安全マージン
3. `--min-remove` 既定 2.5 → 1.0 分
4. チューニングのスナップ範囲 240/90秒 → 120/60秒

**結果**: 演奏を削った量 **982秒 → 0秒**。残差はすべて安全側(不要区間を少し含む方向)。

| 境界 | 提案(改善後) | 正解 | 誤差 | 向き |
|---|---|---|---|---|
| 合奏1 開始 | 00:08:17 | 00:08:42 | −25s | 安全側 |
| 合奏1 終了 | 01:32:36 | 01:30:49 | +107s | 安全側 |
| 合奏2 開始 | 01:39:02 | 01:41:54 | −172s | 安全側 |
| 合奏2 終了 | 03:04:17 | 03:04:00 | +18s | 安全側 |

**この分析の限界も記録されている**(README.md にも記載): 1セッション・4境界での実測にすぎない。
平滑化を外す判断は「ビタビと役割が重複している」という機構的理由からも支持されるが、
`--guard` の120秒という値は他のセッションで見直す余地がある。

### 2.4 転換点E: レコーダプロファイル抽象化(8/14 01:51, `a7916e2` / `d33c36e`)

指示書 `mix_and_profiles.md` §4 の要求により、機種依存部分を切り出した。
設計の核心は「**機種依存なのはファイル探索だけ**」という切り分けにある。

```python
class RecorderProfile:
    def discover(self, root_dir: Path, date: str) -> list[TakeInfo]: ...
    channel_groups: dict[str, list[str]]  # 例: {"ext": ["Tr1", "Tr2"], "int": ["TrMic"]}
    needs_take_concat: bool
```

`channel_groups` が「どのトラックがどの系統に属するか」を表し、
`merge` は「2トラックで1系統ならモノラル2本を左右に組み、1トラックならそれ自体がステレオ」
と解釈する(`orchpipe/merge.py`)。これにより機種固有の分岐がパイプライン本体から消えた。

未実装の2機種はスタブとして残し、**呼び出した瞬間に未実装と分かる**状態にした
(`NotImplementedError`)。実装時に必要な情報は docstring に保存されている
(`orchpipe/recorder_profiles/zoom_f3.py`、`single_file.py`)。

### 2.5 転換点F: `recorder` 設定の情報源一元化(8/14 08:43〜09:12, `1158b87` / `c0dc2c3`)

自己監査(§4.5)で、`propose` だけがプロファイルを無視して系統名
`["ext","int"]` にフォールバックしていることが判明した。
`--recorder zoom-f3` を渡しても `propose` はエラーにならず正常終了していた。

**設計判断**: `--recorder` を `ingest`(と `all`)以外から**削除**し、
下流は `ingest.json` に記録された `recorder` / `channel_groups` を読む形にした。
コミットメッセージ `1158b87` より:

> 下流で機種を指定し直せると取り込み時と食い違う恐れがあるうえ、系統名をコード側に
> 埋め込む必要が生じるため、あえて指定できないようにしてある。

この変更により、系統名のハードコード3箇所(`mix.py` の `block_files` 呼び出し、
`pipeline.py` の `_merged_paths` フォールバック、`propose --source` の `choices`)が
同時に解消された。`--source` は argparse の `choices` をやめ、実行時に
`channel_groups` に対して検証する形に変えている。

続けて、誰も読まなくなった `session_config.json` の `recorder` キーを削除した(`c0dc2c3`)。
**指示書との相違を意図的に選択した例**でもある:

> なお指示書 orchestra_recording_pipeline_mix_and_profiles.md の 2章は
> session_config.json に recorder を含む例を示しているが、この点は指示書より
> 後の判断で意図的に外している。 —— `c0dc2c3`

後に指示書側も更新された(`738d83a`)。

### 2.6 転換点G: 正規化の基準範囲(8/14 12:28, `ef861fc`)

当初はブロックごとに個別のゲインを求めていたため、全ブロックが −1 dBFS に揃い、
「合奏1は大音量、合奏2は静か」といった**演奏どおりの音量差が失われていた**。

`session_config.json` に `normalize_scope` を追加し、既定を `date` に変更:

- **`date`**: 日付・系統ごとに全ブロックの本編ピークの最大値を基準とし、
  そこから求めた**単一のゲインをその系統の全ブロックへ適用**
- **`block`**: 従来どおりブロックごとに個別のゲイン

実データでの効果(260726 ext系統、共通ゲイン −10.71 dB):

| ブロック | 元の最大との差 | 正規化後の差 |
|---|---|---|
| 合奏1 | −0.06 dB | −0.06 dB ✓ |
| 合奏2 | ±0.00 dB | ±0.00 dB ✓ |
| 合奏3 | −0.87 dB | −0.87 dB ✓ |

**元のブロック間の音量差が完全に保存されている**。`block` 単位だと全ブロックが
−1 dBFS に揃い、この差は失われる。

**この工程で判明した重要な事実**: 32bit float 録音のピークが**0 dBFS を超えていた**
(260726 の外部マイクで **+9.65 dBFS**、260802 で +4.08 dBFS)。32bit float なので
ファイル上は壊れていないが、固定小数点で書き出せば激しくクリップする。
**正規化は音量を揃えるだけでなく、後段のエクスポートを成立させるために必須の工程**
であることが実データで裏付けられた。260726 では約 −10.7 dB の**減衰**として働いている。

### 2.7 転換点H: アップロードのスキップ機能(8/15, `b113ed2` / `cc5dd30`)

Google Drive のフォルダ構成変更にともない、同一内容の WAV 3.5 GiB を再送する必要が
生じていた(仕様が「同名は新バージョンとしてアップロード」だったため)。回線 4〜5 MiB/s では
約15分かかる。

この非効率を報告したところ、指示書が更新され、スキップ機能が正式に要求された。

- **Drive**: `md5Checksum` とローカル MD5 を比較(`b113ed2`)
- **Box**: `sha1` とローカル SHA-1 を比較(`cc5dd30`)

**効果**: 260802 の再実行で **3.89 GiB すべてがスキップされ、移行と検証を含めて11秒で完了**
(従来15分)。

3. **クラウド系は client / upload の2層**。`box_client`(API通信)と `box_upload`(段の処理)、

   client と upload を横断的に使う唯一のモジュール(6依存で最多)。

   `box_upload` と `gdrive_upload` の両方から使われる(`20288a5` で共通化)。

### 3.3 最も複雑・重要なモジュール

**`segment.py`(530行、分岐69)が最複雑**。分岐数は2位の `box_client.py`(38)の1.8倍。
理由は、単一のアルゴリズムではなく複数の判定機構が積層しているため:

- 頑健なz正規化(中央値/MAD)と重み付き合成 —— `ensemble_score`
- 大津の方法 + 2クラスk-means による閾値決定 —— `decision_threshold`
- 2状態ビタビ探索 —— `_viterbi`
- 遷移ペナルティの二分探索 —— `_fit_penalty`
- 最小長制約の反復適用 —— `_enforce_min_durations`
- チューニング事象の検出とスナップ —— `find_tuning_events`, `_snap_to_tuning`
- 安全マージンの適用 —— `_apply_guard`
- ラベリングと信頼度算出 —— `_label_segments`

**`features.py`(380行)が技術的な中核**。最長関数は `extract_frame_features`(109行)で、
ffmpeg のパイプからストリーミング処理しながら6種類の特徴量を抽出する。
3時間の音声(約70万フレーム)を、巨大な配列をメモリに載せずに処理する必要があるため
ブロック単位の処理になっている。

**`box_client.py`(422行)が外部連携で最大**。OAuth2 のブラウザ認証フロー
(ローカルHTTPサーバ + CSRF対策の state 検証)、トークンのローテーション対応、
チャンク分割アップロードを含むため。最長関数は `authorize_interactive`(77行)。

## 4. 指示書の分析

6本の指示書はいずれも「何を作るか」だけでなく「**なぜそうするか**」「**何を検証するか**」を
含む構造になっている。各指示書に「検証してほしいこと」の節があるのが特徴。

### 4.1 phase1.md(115行)― 取り込み〜トリミング

**対象範囲**: 取り込み → チャンネル結合 → TAKE連結 → 不要区間の候補提案 → 確認後のトリミング

**最も特徴的な部分は §4「不要区間検出のヒント」**。音響現象を言語化し、
それを特徴量設計に落とす道筋を与えている。

> 練習の構造は概ね以下の繰り返し:
>
> ```
> 音出し → (合図) → チューニング → 合奏 → 休憩 → (合図) → チューニング → 合奏 → 休憩 → ...
> ```
>
> 無音検出だけでは判定できない。以下の音響的特徴を判定ロジックの手がかりにすること:
>
> - **音出し・休憩中**: 各奏者がバラバラに個人練習しており、リズムの統一感がなく、
>   ダイナミクス(強弱)のメリハリが乏しい。強音が途切れず連続する傾向があり、
>   無音区間はむしろ少ない。
> - **合奏中**: 指揮者が頻繁に演奏を止めて指示を出すため、無音・弱音区間が断続的に挟まる。
>   全奏者が揃って演奏するため、音出し時間帯より音響的な統一感(タイミング・強弱の一致)が高い。
> - **チューニング**: 単一の持続音(基準音)に近い、スペクトル的に単純な音が一定時間続く。
>   音出し→合奏の切り替わり直前に必ず出現するため、区間境界の強力な手がかりになる。
>
> これらを組み合わせた特徴量(例: 短時間窓ごとのRMSラウドネス、無音率、音量の分散/変化量、
> ピッチ安定性やスペクトルフラットネスなど)を使い、境界候補にスコアを付けて上位候補を
> 提示する設計にすること。**閾値だけに頼った単純な無音検出は避けること。**

この記述が、実装では以下の特徴量に対応した:

| 指示書の記述 | 実装した特徴量 |
|---|---|
| リズムの統一感 | `pulse_clarity`(オンセット包絡の自己相関ピーク) |
| ダイナミクスのメリハリ | `dyn_range`(RMS の p90−p10) |
| 無音区間の多寡 | `silence_ratio`(適応的閾値による無音フレーム率) |
| 音響的な統一感 | `flux_crest`(オンセット包絡の尖り具合) |
| スペクトル的な単純さ | `flatness`、`tonal`(純音性)、`peak_hz`(放物線補間つき) |

**将来への転用要求**(§7)が、`features` / `segment` の分離を規定した:

> 境界検出ロジックは、将来的に「合奏内の指揮者停止単位でのチャプター分割」や
> 「指揮者発言のみカット」にも転用できるよう、汎用的な特徴量抽出モジュールとして
> 疎結合に設計すること

### 4.2 mix_and_profiles.md(84行)― 正規化・ミックス・プロファイル抽象化

**対象範囲**: トラック単位の正規化、ext/int ミックス、レコーダプロファイル抽象化

**冒頭に明示的なリグレッション条件がある**のが特徴:

> **重要な制約**: この変更は、既存のZOOM M4向けの挙動(260802・260726で検証済みの
> ファイル探索・結合・トリミング結果)を一切変えてはならない。実装後、両日付のデータで
> `ingest`〜`apply`までを再実行し、結果が変わらないことを確認すること(リグレッションチェック)。

**ミックスの安全設計**(§2)は、技術的な主張を含む点で興味深い:

> - `source=mix`: ext_norm・int_normを指定比率で加算合成し、合成後のピークを検出する。
>   0dBFS(または-1dBFS等の安全閾値)を超えていたら、**信号全体を線形にスケールダウン**して
>   安全域に収める。コンプレッサーやリミッターのようなダイナミクスを変える処理は
>   使わないこと(単純な一律ゲイン調整のみ)
>   - 外部マイクと内蔵マイクは同じ音を別位置で拾っている相関の高い信号のため、
>     単純合成すると位相の重なりでどちらの原音のピークよりも高い合成ピークが生まれることがある。
>     **この安全処理は「万が一」ではなく構造的に必要**

**この主張は実装時に反証された**(§5.4参照)。比率の合計が 1.0 以下の凸結合では
三角不等式より超過は数学的に起こりえない。ただし安全処理自体は必要(比率を固定しない
仕様である以上、合計1.0超の設定が取りうるため)。

**プロファイル抽象化の設計思想**(§4)。未実装機種の扱い方が具体的:

> - **`ZoomF3Profile`(スタブのみ、呼び出すとNotImplementedErrorで分かりやすく停止)**:
>   ZOOM F3公式マニュアルで確認したところ、フォルダを掘らずルート直下に
>   `{date}_{番号}.WAV`(ステレオ1ファイルモード)または `{date}_{番号}_Tr1.WAV` +
>   `{date}_{番号}_Tr2.WAV`(モノラル2ファイルモード)が作られる。内蔵マイクがないため
>   `channel_groups`は`ext`のみになる想定。これらは実装時の参考として docstring に残すが、
>   今回はコード本体は実装しない
> - 今回は`ZoomM4Profile`のみ実データ(260802・260726)で検証し、
>   他2つは「**未実装であることが呼び出した瞬間に分かる**」状態にしておく

### 4.4 phase3_box_upload.md(63行)― Box アップロード

**対象範囲**: MP3 を Box へ、パスワード保護・ダウンロード不可の共有リンク発行

**外部ドキュメントの優先を明示**している点が実装方針として重要:

> 正確なAPIのリクエスト・レスポンス形式は、Box公式ドキュメント
> (https://developer.box.com/guides/authentication/oauth2/)を参照して実装すること。
> **本指示書の記載内容と食い違う場合は公式ドキュメントを優先する**

**トークンローテーションへの注意喚起**:

> **重要**: Boxのリフレッシュトークンは使用のたびに新しい値に入れ替わる(ローテーション)仕様。
> トークンをリフレッシュするたびに、新しいリフレッシュトークンを必ず保存し直すこと。
> これを怠ると、しばらくしてから認証が切れ、再度ブラウザでの許可が必要になる

**認可コードの寿命についての実務的な指示**:

> 初回認証フロー: ローカルにHTTPサーバーを起動 → Boxの認可URLをブラウザで開く →
> `http://localhost:8888/callback?code=...`にリダイレクトされる
> (**このcodeは有効期限が短い(数十秒)ので、サーバーは事前に起動しておくこと**)

**検証要求に人間の目視を含む**:

> 実際に生成された共有リンクを(ブラウザで、あるいは可能なら別のAPI呼び出しで)開き、
> パスワード入力を求められること、ダウンロードボタンが出ない(プレビューのみ)ことを
> **人間の目で確認できる形で報告すること**

### 4.5 phase4_gdrive_upload.md(92行、3回改訂)― Google Drive

**最も改訂が多かった指示書**。3つのバージョンが存在する:

| 版 | 構成 | 対象 |
|---|---|---|
| 第1版 | `練習録音/{date}/` | WAV のみ |
| 第2版 | `練習録音/{date}/{WAV,MP3}/` | WAV + MP3、フラット配置からの移行 |
| 第3版(現行) | `orchestra-recording-pipeline/{orchestra}/{date}/{WAV,MP3}/` | + 団体階層、スキップ機能 |

**Box との性格の違いを冒頭で明示**:

> - WAV: 動画担当の動画担当向け。動画編集用の素材としての受け渡しなので、

### 5.4 L/R チャンネル補正の実測検証(8/14 01:51, `317a20b`)

**発端**: 260726 は録音時に外部マイクの Tr1/Tr2 の L/R が配線ミスで逆転していた
ことが判明[セッションログ]。

**対処**: `session_config.json` の `ext_lr_map` を `swapped` に設定し、
`merge --groups ext --force` で外部マイク側のみ再結合。

**検証1: 結合直後のチャンネル対応**

```
チャンネル検証 (swapped): |L-Tr2|=0.00e+00  |R-Tr1|=0.00e+00  |L-Tr1|=5.47e-01
```

L に Tr2、R に Tr1 が**ビット単位で完全一致**。`|L-Tr1|` が 0 でないことが補正の証拠。
また `int` 系統は sha256 で無変更を確認(`--groups ext` により対象外)。

**検証2: 境界検出への影響がないこと**

L/R を入れ替えても `candidates.json` の7区間すべてが `confirmed.json` と完全一致した。

**理由も特定**: 特徴量抽出は ffmpeg の `-ac 1` でモノラルにダウンミックスした信号を
入力にしている。ステレオ→モノラルは L と R について対称((L+R)/2)なので、
**L/R を入れ替えても入力信号自体が完全に同一**になる。境界が一致するのは偶然ではなく
構造的な帰結である。

**検証3: 最終成果物までの伝播**

`apply --groups ext --force` 後、trimmed の ext 3本は変化・int 3本は同一を sha256 で確認。
さらに `01_合奏1_ext.wav` の L/R を元トラックと直接比較:

```
|L - Tr2| = 0.00e+00   (補正後、左には Tr2 が来るのが正しい)
|R - Tr1| = 0.00e+00
|L - Tr1| = 4.67e-01   (0でないことが補正された証拠)
```

**検証4: 正規化・ミックス後まで**

`01_合奏1_final.wav` の左チャンネルを、元の Tr2 に正規化ゲイン(−10.65 dB)を掛けた
ものと比較:

```
|L − Tr2×gain| = 6.4e-06   (ほぼ一致。誤差は32bit floatでのゲイン演算による丸め)
|L − Tr1×gain| = 1.4e-01   (明確に不一致 = 補正が効いている)
```

配線ミスの補正が `merge` → `apply` → `normalize` → `mix` を通って最終ファイルまで
正しく伝播していることが確認された。

**指示書との関係**: `mix_and_profiles.md` §7 は「`ext_lr_map=swapped` を指定した場合に、
実際にL/Rが入れ替わって出力されることを**合成データで検証する**」と要求していたが、
ユーザーの判断により「実データでの検証の方が価値が高い」として上記の実データ検証で
代替した[セッションログ]。

### 6.3 アルゴリズムのアブレーション・パラメータ探索

**平滑化長のスイープ**(§2.3):5水準(0 / 30 / 60 / 120 / 300秒)で境界誤差を測定。
60秒を境に破綻することを発見。

**`--splits` の頑健性**:2〜8 の5水準で区間の連続性・最小長・全長一致を検証。
`splits=8` で guard が休憩を1秒まで潰すバグを発見し、隣接区間の60%までに制限する形で修正[セッションログ]。

**閾値推定手法の比較**:大津の方法(2.07)/ 2クラスk-means中点(2.08)/ KDE谷(−1.35)を
比較し、いずれも望ましい値(約1.0)から外れることを確認。最終的に
「大津 − 中心間距離の25%」を採用。

**境界リファインメント手法の比較**:最大コントラスト法(最大誤差310s)、
持続クロッシング法(113s、hold値に対して不安定)を試したうえで、
いずれも単純な「平滑化なし」(102s)を上回らないことを確認し、不採用とした。

**正規化スコープの検証**:合成データで元ピーク ext[−6, −12] dBFS に対し、
`date` は共通ゲイン +5 dB で [−1, −7](6 dB の差を保存)、
`block` は個別ゲイン +5/+11 dB で [−1, −1](差が消える)ことを理論値どおりに確認(`ef861fc`)。

**ミックス安全処理の検証**:指示書の主張(位相加算で超過する)を検証するため、
相関の高い2信号を合成データで作成。結果:

| 比率 | 理論合成ピーク | ffmpeg 実測 | 動作 |
|---|---|---|---|
| 0.6 : 0.4(合計1.0) | −1.42 dBFS | −1.42 dBFS | 調整なし |
| 1.0 : 0.8(合計1.8) | +3.66 dBFS | +3.66 dBFS | −4.66 dB スケールダウン → **−1.00 dBFS** |

理論値と実測値が完全一致。**凸結合では超過が起こりえない**ことを示し、
安全処理の発動条件が「位相の重なり」ではなく「比率の合計が1を超えること」であると特定した。

### 6.4 2データセットでの相互検証

260802(2ブロック)と 260726(3ブロック)は、単なる件数の増加ではなく
**異なる条件を突く組み合わせ**になっている:
